# ADR 0001: Wrap the harness2 CLI and read its files; never import its Python

- **Status:** Accepted. Part of the v1.0 contract ([ARCHITECTURE.md](../ARCHITECTURE.md) §2).
- **Applies to:** `h2s-core` (command lines, parsers, results reader), `h2s-daemon` (job engine).

## Context

harness2 is a Python research framework. It has no library API: what it offers to the outside is
a set of console scripts (`harness2`, `harness2-demo`, `harness2-setup`, `harness2-check`,
`harness2-judge`, `harness2-report`, `harness2-bridge`), a handful of environment variables, and the
directory layout it writes under `HARNESS2_RUNS_DIR`. Its internals (module layout, function
signatures, the OpenCode and Codex runners) change with the research.

The Studio is a Rust program that must start those tools, follow them, and show what they wrote,
without a terminal, for several users, with credentials in play.

## Decision

1. **Run harness2 only through its console scripts**, as child processes of the server. The
   argument vector is built by `h2s_core::cli` from validated, typed parameters; it is never a shell
   command line, no value may start with `-`, and every identifier passes `h2s_core::names` first.
   The environment is built from nothing (`env_clear()` plus a fixed pass-through and the profile's
   variables). Each step gets its own process group so that cancellation reaches everything below it.
2. **Read results as files.** `h2s_core::results` walks the experiment directory through `cap_std`
   handles and parses the JSON and Markdown harness2 wrote. The directories stay ordinary harness2
   directories: upstream's own tools keep working on them.
3. **Parse progress from output.** `h2s_core::parse` turns harness2's stdout (`[domain] i/n status
   task`, previews, judge and report blocks) into typed results. The parsers are verified against
   output captured from the real tools.
4. **Port, don't embed, the few pure computations** the UI needs (report rendering, harness-tree
   validation, harness fingerprints, namespaces) as byte-exact Rust code checked against fixtures
   generated by upstream's own Python (`tests/fixtures/`, `docs/notes/core.md`).
5. **Pin what was tested**: `TESTED_HARNESS2_COMMIT` in `h2s-core`. The managed installer fetches
   exactly that commit by hash; `doctor` warns when the installed commit differs.
6. **Never import harness2's Python**, and do not modify harness2 (a non-goal of the contract).

## Consequences

Good:

- A crash, hang or memory blow-up in harness2, OpenCode or a model-written script cannot take the
  server down; it ends one process group, which the server can kill, time out and account for.
- The Studio has no Python in its own process, no GIL, no interpreter-version coupling and no
  foreign-function build step. It runs against any harness2 that keeps the CLI and layout.
- Results remain portable: copy an experiment directory to another machine, or open it with
  harness2's tools, with or without the Studio.
- The same argv works in a container (`docker run ... <image> <program> <args>`), which is what makes
  container isolation ([ADR 0006](0006-isolation-modes.md)) a wrapper rather than a rewrite.

Bad, and how it is managed:

- **Coupling to flags and output formats.** An upstream change to a message or a flag breaks a
  parser. Mitigations: the commit pin; fixtures of real captured output; a release-checklist step to
  re-check flags and formats when the pin moves ([RELEASING.md](../RELEASING.md)); `doctor` flags drift.
- **Duplicated logic can drift.** The ports of `report`, `tree.validate` and the fingerprint must
  keep matching upstream. They are checked against goldens produced by upstream code, and the
  deliberate differences are written down (no byte-compilation of scripts; symlinks are never
  followed).
- **Process-per-step overhead** and progress by text parsing instead of structured events.
- **Whole-process control only.** There is no way to ask harness2 to pause, change a setting mid-run
  or stream structured events; cancellation is a signal to a process group.
- **Host-path coupling.** Summaries record absolute run directories; the reader maps them under the
  experiment (or the container mount point) or refuses them.

## Alternatives considered

- **Embed Python with PyO3** (rejected, in the original decision table). It couples the server to
  harness2's internals and to a particular interpreter, puts model-written-code-adjacent machinery
  in the server's address space with no isolation of crashes, and makes every harness2 refactor a
  Rust build problem.
- **Fork or patch harness2** to add a library API or structured output. Ruled out by the contract's
  non-goals ("modifying harness2 itself"): the project wants to follow upstream, not maintain a
  fork. The cost is the parsing described above.

## Evidence in the repository

`crates/h2s-core/src/cli.rs`, `parse.rs`, `results.rs`, `install.rs`;
`crates/h2s-daemon/src/jobs/core_backend.rs`; `tests/fixtures/README.md`; the real harness2 demo
runs through the server in `crates/h2s-e2e/tests/server_demo.rs`.

## Revisit when

harness2 publishes a stable library or structured (JSON) output mode, or when keeping the parsers
in step with upstream costs more than the isolation is worth.
